# zk-verifier security-fix redeploy — 2026-07-27/28

Redeploy record for the P0 fix in `docs/SECURITY_AUDIT.md` section 2.10:
`require_owner_or_gov` used to trust a caller-supplied `governance_approved: u64`
flag with zero on-chain verification, letting any account bypass owner
control of `register_vk` / `disable_vk`. Fix landed in commit `859a641`
(2026-07-27) but could not be deployed to testnet at the time — this doc
covers the actual redeploy once the root cause of the deploy failures was
found.

## Root cause of the "can't deploy" blocker (not an API-key problem)

Three, then two more, `installOrUpgrade` attempts from `anna-stolbovskaja`
(the account that owns all other 8 CP contracts) reverted identically with
`ApiError::InvalidArgument [3]`, at near-identical gas cost, **regardless of
wasm content** — including a control redeploy of the unmodified original
source. This was initially misdiagnosed as a `CSPR_CLOUD_API_KEY`/auth
problem. It was not: a real, valid CSPR.Cloud key produced the exact same
revert.

Actual cause, confirmed by inspecting the account's live NamedKeys via
`state_get_entity`: `storage::new_dictionary()` / `storage::new_uref()`
write their NamedKey directly onto the **calling account's** context, and
Casper rejects the call if a key with that exact name already exists there.
`anna-stolbovskaja` already held `vks` / `verdicts` / `verifiers` (and other
per-contract keys) from the *first* zk-verifier install, months earlier —
already documented generically for a different contract in
`docs/DEPLOYMENT_LESSONS.md` Lesson 3, but not connected to this failure
until now. `zk-verifier`'s `call()` has no upgrade-safety guard: it always
tries to (re)create those dictionaries.

**Renaming the dictionary/owner/paused constants to a `_v2` suffix, deployed
from the same `anna-stolbovskaja` account, still reverted identically** —
ruling out that the specific literal names were the only issue and
confirming the Lesson-3 prescribed fix (clean wallet) as the real one.

## Fix applied

1. Generated a fresh secp256k1 testnet keypair (never used for any prior CP
   deploy) and funded it with 300 CSPR from `anna-stolbovskaja`.
2. Verified via `GET /accounts/{hash}` and `state_get_entity` that the new
   account had zero pre-existing NamedKeys before deploying.
3. Deployed the fixed `zk-verifier` wasm (commit `859a641` + this doc's
   commit, 105/105 contract-tests green, MVP-clean, 53029 B) from that clean
   account. `error_message: null` on the deploy — success.
4. Live regression-tested the actual security property, not just the
   deploy: called `register_vk(governance_approved=1, ...)` signed by
   `anna-stolbovskaja` (now a non-owner) → reverted `User error: 1`
   (`ERR_NOT_OWNER`), confirming the bypass is closed. Called the same entry
   point signed by the new owner key → succeeded (`error_message: null`).

## ⚠️ Known inconsistency, flagged not hidden

The owner/admin key for `register_vk` / `disable_vk` / `pause` / `unpause` on
this contract is now the **new dedicated deployer key above, not
`anna-stolbovskaja`** — the only one of CP's 9 contracts where the owner
account differs from the other 8. The contract has no `transfer_owner`
entry point, so ownership cannot be rotated back to `anna-stolbovskaja`
in-place. This mirrors the precedent set by the governance contract redeploy
(`docs/roadmap/GOVERNANCE_DEPLOY_2026-07-26.md`), which also switched
deployer accounts to escape the same class of NamedKey collision.

The new deployer secret key was generated by Viktor in-sandbox and has not
been handed to a human yet — Andrea should treat it as sensitive and decide
whether to take custody of it or leave it managed by the agent sandbox.
